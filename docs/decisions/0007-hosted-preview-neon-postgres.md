# ADR 0007: Move the hosted preview database from PGlite to Neon PostgreSQL

Date: 2026-09-03
Status: accepted

## Context

ADR 0006 selected Netlify Free plus Render Free for the initial public preview, with the Render API running `AJANI_DATA_MODE=pglite` against an ephemeral `/tmp` directory. That Render build reached application startup, but PGlite's in-process WASM engine then exceeded Render Free's 512 MiB memory limit under real use. Render's own free managed PostgreSQL was considered and rejected: it has a fixed database-expiry date, which does not fit an ongoing public preview. The repository already has a complete, tested external-PostgreSQL path (`AJANI_DATA_MODE=postgres`, `DATABASE_URL`, the same Drizzle schema and migrations, and a dedicated CI job exercising real PostgreSQL concurrency) — the correction only needed to route the hosted API onto that existing path against a small external database, rather than invent a new one.

This ADR amends the storage-topology part of ADR 0006 for the hosted API only. ADR 0006's choice of Netlify for the frontend, Render for the API, and the general shape of the free-tier split remain unchanged and are not rewritten here.

## Decision

Use Neon Free PostgreSQL as the hosted API's database. `render.yaml` sets `AJANI_DATA_MODE=postgres`; `DATABASE_URL` is a secret added manually in the Render dashboard once Neon supplies it, never committed. No Render PostgreSQL resource and no Render persistent disk are added — Neon is external to Render, exactly like any other `AJANI_DATA_MODE=postgres` deployment this repository already supports.

Because a public preview with no authentication must start from a clean, working state on every cold start rather than accumulate every visitor's mutations forever, `render.yaml` also sets one new environment variable, `AJANI_HOSTED_PREVIEW_RESET=synthetic-preview-only`. This is deliberately a separate setting from `AJANI_DATA_MODE`, and deliberately a specific phrase rather than a boolean: an ordinary `AJANI_DATA_MODE=postgres` deployment (someone else's real external-PostgreSQL use of this codebase, or a future non-preview deployment) must never auto-reset just because Postgres mode is selected. Only the exact approved value arms it; anything absent, misspelled, or merely truthy leaves it disabled, and enabling it against an incompatible mode (for example alongside `AJANI_DATA_MODE=pglite`) is a startup configuration error, checked before any database connection opens.

The reset itself is a dedicated function, `resetHostedSyntheticPreviewPostgres`, separate from the existing PGlite-only `resetSyntheticPreview`. Neither guard was loosened to serve the other: the existing function still refuses anything but explicit PGlite use, and the new one refuses anything but explicit PostgreSQL use. It reuses the existing scoped delete logic (the known synthetic-preview organisation and everything hanging off its fixed persona IDs, already proven to catch visitor-created rows, not just the static seed) and the existing seed logic, but runs delete-then-reseed inside one transaction rather than the PGlite path's two sequential ones, so a hosted cold start never observes a half-reset database. `apps/api/src/server.ts` calls this — migrate, then reset — before `application.listen(...)`, and deliberately discards the original error and substitutes a fixed, credential-free message if anything in that sequence fails, since a database driver's own error text is not a value this codebase controls closely enough to trust with a connection string.

`packages/database`'s connection and migration modules now import the PGlite runtime (`@electric-sql/pglite`, `drizzle-orm/pglite`, `drizzle-orm/pglite/migrator`) lazily, only inside the branch that actually selects `AJANI_DATA_MODE=pglite`. This is in addition to, not a replacement for, moving off PGlite in production: even a PostgreSQL-mode process should not pay to load an engine it will never use. The postgres.js client's own pool stays deliberately small (`max: 3`) for a single free-tier instance against a single free-tier database branch, and `prepare: false` is kept because managed-Postgres connection poolers, Neon's included, commonly don't support server-side prepared statements across pooled connections.

## Consequences

- The hosted API no longer risks PGlite's in-process memory growth; Render Free's 512 MiB limit now only has to cover the Node process and a small `postgres.js` connection pool.
- Neon's data is persistent storage, unlike PGlite's ephemeral filesystem — but the application still deliberately clears and reseeds its own known scope on every start, so the operational behaviour visitors experience (a clean, shared, resettable demonstration) is unchanged from the PGlite-era description in ADR 0006. Nothing outside that scope should exist in this database, and the reset does not touch anything it does not recognise.
- Local development and every automated test keep using PGlite exactly as before (`npm run dev`, `npm run test:database`, `npm run test:e2e`, `npm run db:verify`) — this decision changes only where the hosted API's data lives, not the project's local or CI default.
- Two free-tier services (Render and Neon) can each independently cold-start after inactivity; a request immediately after a long idle period may see both delays compound. `/ready` reflects this honestly by performing a real database query; `/live` deliberately does not.
- A new manual step is required before merging the change that flips `AJANI_DATA_MODE` to `postgres`: `DATABASE_URL` must already be set on the existing Render service, or the API fails its next deploy with a clear configuration error rather than an unsafe fallback.
- Neither Neon's nor Render's free tier is a permanent guarantee; both remain subject to the providers' own future limits and pricing. This decision does not claim otherwise, and does not represent production healthcare-hosting approval any more than ADR 0006 did.
- A later move to a paid, always-on, or differently-pooled database tier remains possible without further application changes, because the hosted path is the same `AJANI_DATA_MODE=postgres` / `DATABASE_URL` seam any external PostgreSQL deployment already uses.
